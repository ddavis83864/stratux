# v2.0.0-rc2 — Release Candidate 2

**Supersedes [v2.0.0-rc1](v2.0.0-rc1.md)**, which was never published (still a draft GitHub
Release, zero downloads) when a real defect was found: GitHub silently rewrites `~` to `.`
in uploaded asset filenames, so `SHA256SUMS` (generated with the correct tilde-bearing
Debian version string) referenced filenames that didn't match what was actually published.
Fixed by deriving published filenames from the git tag itself (already GitHub-safe, no `~`
possible in a git ref) instead of from the Debian package version string - see
`.github/workflows/release.yml`'s own updated comments. The `v2.0.0-rc1` tag itself was
never moved or deleted; only its own broken, unpublished draft release was removed. No other
change from rc1.

**Status: Release Candidate. Not a stable release.** See
[release-process.md](../release-process.md) for what separates the two and the promotion
plan. This document is filled in progressively as this release candidate's own validation
proceeds; it is complete only once every section below carries real, dated evidence rather
than a placeholder.

Base commit: `b8699d9637dcca8f27b7ed699a8ef52ec25668ae` (`master`, PR #24 merge, built on
`732ac2cfb04dd9918e8fd7286eaedf6784a91667`/PR #20).
Package/display version: `2.0.0~rc2` (correctly incremented from rc1's `2.0.0~rc1`, since
`getversion.sh` derives it from the nearest tag - confirmed against the actual built
package's own `Version:` field, not assumed). Tag: `v2.0.0-rc2`. Verified with
`dpkg --compare-versions`: `2.0.0~rc2` sorts after `2.0.0~rc1` and before `2.0.0`, as
expected.

## New capabilities since the last upstream tag (`v2.0-pre5`)

See [CHANGELOG.md](../../CHANGELOG.md) for the complete, per-PR feature-to-documentation
mapping. In summary, this fork adds: a readiness/health model with trusted GNSS time and
persistent-storage certification; AHRS/barometer/fan health; named aircraft calibration
profiles; a preflight readiness workflow; traffic and system-health alerting including
closure-rate/CPA trend detection; Configuration Backup and Restore; power/thermal health and
a controlled-shutdown workflow; a Storage Lifecycle inventory foundation; Automatic Flight
Recording (disabled by default); a hardened, OTA `StageFailed` recovery path with a
supported reset; and Wi-Fi Administration Hardening, replacing the previous unguarded
Wi-Fi settings path entirely.

## Correctness and safety fixes

- Network mutex/concurrency initialization fix (PR #5).
- `/setSettings` malformed-input panic fix (PR #11).
- Monotonic-clock and settings-mutation data races (PR #18).
- OTA `StageFailed` unbounded-retry defect, the incident that motivated PR #22's bounded
  recovery policy and `/resetOTA`.
- Three real hardware-validation defects found and fixed during PR #20's own validation:
  a reconnect-token race, a browser-caching defect that could mask an already-deployed fix,
  and a legacy `/setSettings` Wi-Fi bypass that circumvented the new hardening entirely — see
  PR #20 for the complete account.

## Operational behavior changes

- **Wi-Fi configuration must now go through the Wi-Fi Admin page** (`/previewWifiAdminSettings`
  → `/applyWifiAdminSettings` → `/confirmWifiAdminReconnection`). The old Settings-page Wi-Fi
  form is gone, and `/setSettings` rejects all ten legacy `WiFi*` fields outright (400) rather
  than silently applying them.
- A stuck OTA `failed`/`recovery_required` state now has a supported recovery path
  (`POST /resetOTA`) instead of requiring manual SSH intervention.

## Compatibility notes

- No settings-schema migration is required for this release — every new settings section
  defaults safely on a device that has never configured it.
- Configuration Backup's schema (2) is unchanged by this release; its own legacy-format
  (pre-PR-14) compatibility layer is untouched.

## Default-disabled features

- Automatic Flight Recording (opt-in).
- The FIS-B weather cache (PR #15) — **excluded from this release entirely**, not merely
  disabled by default. No `fisbcache` code, dashboard page, settings section, or
  documentation is present. Verified by commit-reachability (`git merge-base --is-ancestor`)
  and by a direct file-tree search of the release commit for every `fisbcache`-named path —
  see Phase 1 evidence in this release's engineering record.

### Build integrity and reproducibility

Two independent, from-scratch clones of commit `c493c5dd` (this release-preparation
branch's own head before the merge), each built with `make dpkg` under the same native
amd64 Docker toolchain used throughout this fork's own validation work. Compared: package
size, whole-file SHA-256, `control.tar.xz`/`data.tar.xz` SHA-256, and a full `diff -rq` of
the decompressed file trees.

**Result: functionally reproducible, not bit-for-bit.** File *content* is identical across
every single file in the package except one: `stratux.appcache`, which differs only in its
own deliberate, pre-existing `# build time: <unix timestamp>` comment (an intentional
browser-cache-busting mechanism, not a defect - see PR #20's own account of this same
file). The whole-`.deb` and `.tar.xz`-level hashes differ between the two builds, but that
difference is fully attributable to conventional build-process metadata (per-file
modification timestamps set by each separate `make dpkg` invocation, embedded in the tar
archive - confirmed by inspecting `tar tvf` entry timestamps directly), not to any
behavioral or content nondeterminism in the build itself.

Not pursued further: normalizing build-time file timestamps (e.g. `SOURCE_DATE_EPOCH`-style
reproducible-build tooling) to achieve true bit-for-bit reproducibility was judged a
separate, larger engineering effort outside this release's own scope - documented here
as a known, accepted limitation rather than silently claimed as already solved.

### Automated test results

Full production Go test suite run under `-race` (native amd64 Docker toolchain,
`stratux_native_amd64_gotools`), covering every package this fork's own PRs #1-#22 added or
touch: `alerting`, `autorecord`, `calprofile`, `common`, `configbackup`, `main`, `ota`,
`power`, `preflight`, `readiness`, `recording`, `sdrassign`, `storagelifecycle`, `trafficcpa`,
`wifiadmin` — all green.

**One genuine, previously-undetected data race found and fixed**: `storagelifecycle.
Manager.Status()` only held its mutex around the initial inventory read, leaving two calls to
`m.monitor.Observe(...)` (which mutates `Monitor`'s own unsynchronized fields) completely
unprotected — caught by `TestManager_ConcurrentScansCoalesceWithoutDataRace`, a test that
already existed specifically to prove this never happens. Confirmed pre-existing at the PR
#20 baseline (`732ac2cf`), predating this release-preparation branch entirely — this fork's
own CI (`ci.yml`) never exercised the full suite under `-race` (its own `make dgotest` target
only covers the narrow `sdrassign` package), so it had never been caught before. Fixed by
extending the mutex's scope to the whole method; verified with 10 repeated `-race` runs and a
full-suite re-run with zero regressions.

**Pre-existing, out-of-scope findings** (confirmed identical at the PR #20 baseline, i.e. not
introduced by this release-preparation work, and never touched by any of this fork's own
PRs #1-#22):
- `godump978` and `uatparse` (both upstream-inherited, pre-fork code) fail `go test`'s own
  built-in vet gate on pre-existing `go vet` findings (a C-char-to-string conversion warning
  and two `Fprintf` format-argument-type warnings). `go vet ./...` output is identical at
  both commits.
- `gofmt -l` flags 29 pre-existing, upstream-inherited files, identical at both commits (this
  release's own new `scripts/gensbom/main.go` was gofmt-clean before being committed).
- `TestAutoRecordAwaitMountAndReload_ReloadsOnceMountBecomesReady` (`main` package) is an
  already-known, independently-flaky race in the unrelated autorecord-mount-detection
  subsystem, first identified and classified during this fork's own PR #20 hardware
  validation — reconfirmed here as still present and still unrelated.

`go vet` and `gofmt -l` otherwise clean on every file this release-preparation branch itself
touches.

### Image identity and sanitization

`stratux-2.0.0-rc2.img.xz`, 574,591,100 bytes compressed / 2,596,274,176 bytes (2.42 GiB)
raw, SHA-256 verified against `SHA256SUMS`, `xz -t` integrity confirmed. Partition table:
standard `dos` label, 512 MiB FAT32 boot + 1.9 GiB ext4 root — matches the expected
Raspberry Pi OS layout.

Mounted both partitions read-only (loop device, never written to) and swept the entire root
partition for: owner-identifying strings (username, email, private backup paths — **zero
matches** anywhere outside expected package documentation paths), `DiagCheck99` (zero
matches), recordings/diagnostics/calibration-profile/OTA-state-backup directories (**none
present** — clean, uninitialized state), `authorized_keys` files (**none** — no unexpected
pre-authorized SSH access), shell history files (**none**), `/etc/machine-id` (**empty** —
regenerates correctly on first boot), MAC-address-shaped strings (found only inside
commented-out documentation examples in the *stock Debian* `/etc/dnsmasq.conf` template,
never in Stratux's own generated `/etc/dnsmasq.d/stratux-dnsmasq.conf`, which contains only
the default `192.168.10.0/24` range), coordinate/token/API-key/secret patterns (zero
matches in Stratux's own config), and the `stratux.service` systemd unit (present, correctly
configured, not pre-started).

Default configuration confirmed: Wi-Fi SSID `Stratux`, open security (`key_mgmt=NONE`),
`stratux.conf.default` matches the documented default (`UAT_Enabled: true, OGN_Enabled:
false, DeveloperMode: false`), `/mnt` and `/media` empty (no persistent-data-partition
residue baked in).

**One expected, already-documented finding, not a new defect**: SSH host keys *are* present
in the image (generated once, at build time, by the CI runner — not any owner's own keys),
matching `known-limitations.md`'s own prior documentation of `regenerate_ssh_host_keys`
being deliberately disabled to minimize first-boot SD-card writes.
